# Sprint team: Frontend, CI/CD & Dual Reviewers

The sprint team currently focuses on **Frontend design and CI/CD implementation**, supported by two independent review agents. Each agent owns a specific lane of the repo to avoid conflicting edits.

The **lead** is whoever started the sprint: the human, or the main session acting for them. The lead assigns work, carries handoff notes between agents, and is the only one who talks to the human. The lead does not write lane code.

Rules in `AGENTS.md` apply to every agent. This file adds the team rules on top.

## Mandatory Repo Grilling Protocol

Before implementing or modifying **ANYTHING** in the project:
1. **Never implement silently**: Agents must not jump directly into writing code without first establishing a shared understanding with the user.
2. **Invoke Grilling (`.agents/skills/grilling`)**: Frame design decisions as structured rounds:
   ```markdown
   ❓ **Q<n>** - **<Question Title>**: <Context, pipeline impact, alternatives>
   ➡️ <Recommended answer and architectural rationale>
   ```
3. **Pipeline Education**: The grill must explicitly explain the end-to-end pipeline involved (Client ↔ Next.js Proxy ↔ FastAPI ↔ PostgreSQL/Supabase ↔ CI/CD) and how the change contributes to forming the overall project.
4. **User Confirmation**: Only proceed with implementation after the user confirms or adjusts the answers.

A file outside every lane (`AGENTS.md`, `GLOSSARY.md`, `docs/adr/**`, `docs/agents/**`, `.claude/**`) is changed only by the lead.

When a task needs a change in another lane, do not make it. Write a request in your handoff note and the lead routes it to the owner.

### Files with one writer

These files cause most merge conflicts, so each has exactly one writer.

- **`package-lock.json` and all dependency lists**: CI/CD. Any agent that needs a package asks for it by name, version and workspace. CI/CD installs from the repo root (`npm install <pkg> -w <workspace>`) and commits it alone as `chore(deps)`.
- **`packages/shared-types/openapi/backend-v1.json`**: Backend. It is generated by `python -m app.export_openapi` in `apps/backend` and never edited by hand. `tests/test_openapi_contract.py` fails when it is stale.
- **`packages/shared-types/fixtures/plan-vectors.json`**: Backend. A change here must keep both parity suites green (`apps/backend/tests/test_quiz_and_plan.py` and `apps/web/src/lib/__tests__/plan-parity.test.ts`).
- **Alembic migrations**: Backend, one migration branch at a time. Never edit a migration that is already on `main`.

## The four phases

Every sprint runs these phases in order. A phase ends at its gate, and the lead confirms the gate before the next phase starts.

### Phase 1: Contract

Agents agree on the API before anyone builds against it.

1. **Backend** writes the request and response schemas and the route signatures for the sprint, then regenerates the OpenAPI file.
2. **UI/UX** checks the contract against every screen state it must draw (loading, empty, error, success) and lists what is missing.
3. **CI/CD** lists the new environment variables, pipeline changes and e2e flows the sprint needs.
4. **Reviewer** turns the sprint's Definition of Done into an acceptance checklist with one verifiable line per item.

**Gate:** the OpenAPI file is committed. From here the contract is frozen.

### Phase 2: Build

The three building agents work at the same time, each in its own lane.

- UI/UX builds against the committed contract and the types in `packages/shared-types`. It does not wait for the backend to be finished.
- A contract change goes back to Backend as a request. Backend changes the schema, regenerates the OpenAPI file and tells the lead. No agent works around a contract gap in its own lane.
- Each agent runs its own lane's checks (below) before handing off.

**Gate:** all three handoff notes are in, each with passing check output.

### Phase 3: Integrate

1. Lanes merge in this order: Backend, then UI/UX, then CI/CD.
2. CI/CD runs the whole pipeline locally the way CI does, including `npm run e2e`.
3. A failure goes to the agent that owns the failing file. CI/CD does not patch another lane to get green.

**Gate:** every job in `.github/workflows/ci.yml` passes on the integrated branch.

### Phase 4: Review and close

1. **Reviewer** checks the integrated branch against the acceptance checklist from Phase 1 and the checklist below, and returns a report.
2. Each blocker goes to the owning agent. After the fix, Reviewer re-checks that finding and reruns the full suite.
3. The lead posts the final report on the sprint's GitHub issue. Only the human closes the sprint.

**Gate:** Reviewer verdict is PASS and the human accepts it.

## Rules for each agent

### Backend

- Routers live in `app/api/v1/endpoints/` and are registered in `app/api/v1/router.py`. A router validates input, calls a service and returns a response model. Business logic and formulas live in `app/services/`.
- Request models and response models are separate Pydantic classes in `app/schemas/`. A response model lists its fields explicitly, so a new database column is not exposed by accident.
- The user comes from the session dependency in `app/api/deps.py`. Never read a user id from the path, query or body. Every query on user-owned data filters by `current_user.id`. Another user's resource returns 404.
- A new user-owned table gets a row-level-security policy (`app/services/rls.py`) and a test in `tests/test_postgres_rls.py`.
- A model change ships with its Alembic migration in the same commit.
- A formula has one implementation, in a service. When the web app must compute the same number, add vectors to the parity fixture.
- Do not log request bodies, measurements, photos, journal text or tokens.
- Checks before handoff, in `apps/backend`: `python -m pytest -q`, `alembic upgrade head`, `alembic check`, `python -m app.export_openapi` followed by a clean `git diff` on the OpenAPI file.

### UI/UX

- Colours, spacing and backgrounds come from `@g-ai/ui` tokens. Change a shared token in `packages/ui`, not in a page.
- Follow the navigation rules in `AGENTS.md` (`homeUrl()` for the logo, `BackLink` for back).
- Call the backend only through `apps/web/src/lib/api-client.ts` on the same-origin `/api/v1/*` path. Never call the backend's own origin from the browser.
- Use only fields that exist in the contract. Do not recompute a backend formula in the client unless a parity test covers it.
- Accessibility target is WCAG 2.2 AA: every control is reachable and operable by keyboard, has a visible focus ring and an accessible name; a timer or live counter announces through `aria-live="polite"` at sensible intervals, not every second; colour is never the only signal.
- Every data view has loading, empty and error states. Layouts work from 360px wide up to widescreen.
- Animation, video and 3D follow `docs/agents/motion-media.md`.
- Checks before handoff, in each app touched: `npm run typecheck`, `npm run lint`, `npm test` (web), `npm run build`.

### CI/CD

- The rewrite `/api/v1/:path*` in `apps/web/next.config.mjs` already covers new routers. Verify a new route through the proxy; do not add a rewrite per route.
- A new environment variable is added to the matching `.env.example` and to `docs/deploy-vercel.md` or `docs/deploy-render.md` with a placeholder. Real values are never written to the repo, a workflow file or a log.
- Each sprint's core flow gets one Playwright spec in `e2e/`. Locate elements by role and accessible name, which also tests accessibility. Wait on conditions, never on fixed delays.
- Never make CI green by skipping, deleting or loosening a test, or with `continue-on-error`. Report the failure to the owning agent.
- Workflows keep `permissions: contents: read` unless a job needs more, and then only that job.
- Deploys, production environment variables, and Vercel or Render project settings change only with the human's approval in that conversation.
- Checks before handoff: the full CI job list run locally, then `npm run e2e`.

### Code Reviewer

- Read-only. Never edits product code and never fixes what it finds.
- Focuses on the immediate diff and code-level quality:
  - **Code Standards:** Coding style, naming, ESM usage, dead code, excessive abstraction (`ponytail-review`), and DRY principles.
  - **TypeScript Safety:** Zero type assertions (`as`), explicit types on exported functions, no `any`, strict compiler options satisfied.
  - **Test Quality:** Unit tests test real behavior; tests fail when behavior is broken; no brittle snapshot assertions.
  - **Accessibility & Motion:** Keyboard navigation, visible focus rings, aria labels, and compliance with `docs/agents/motion-media.md`.

### Codebase Reviewer

- Read-only. Never edits product code and never fixes what it finds.
- Focuses on the larger architecture, system integrity, and end-to-end pipeline:
  - **Pipeline Consistency:** Verifies how the change flows across Client ↔ Proxy ↔ Backend ↔ Database ↔ CI/CD. Ensures no bypass of the Next.js reverse proxy or direct Supabase exposure.
  - **Security Audit:** OWASP Top 10, Row-Level Security (RLS) enforcement, least privilege role separation, cookie flags (`httpOnly`, `Secure`, `SameSite`), zero PII/health data in client storage or logs.
  - **Contract & Parity:** Verifies OpenAPI parity, schema isolation (request models never accept `user_id`), and math parity against `plan-vectors.json`.
  - **Performance & Resources:** Bundle size impact, no 3D on live workout view without proof of 30 FPS, lazy loading of heavy assets.

Both reviewers report in the standard format:
- Verdict: `PASS`, `PASS WITH FOLLOW-UPS`, or `FAIL`.
- One finding per line: severity (`blocker`, `major`, `minor`), `file:line`, owning agent, what is wrong, and the command/proof.
- Acceptance checklist marked met or not met.

## Handoff note

Every agent ends its turn with this note. The lead passes it on unchanged.

```
Lane:        ui-ux | devops | code-reviewer | codebase-reviewer | backend
Phase:       1 | 2 | 3 | 4
Done:        what now works, in one or two lines
Files:       paths changed
Checks:      each command run and its result
Requests:    changes needed in another lane (owner, file, what, why)
Not done:    anything skipped or unverified, and why
```

## Git

- One branch per lane per sprint: `feat/s<sprint>-<lane>-<slug>`, for example `feat/s1-backend-nutrition`. Never commit to `main`.
- Conventional Commits with a scope, matching the history: `feat(backend)`, `feat(web)`, `fix(nav)`, `test(e2e)`, `chore(deps)`, `ci`.
- Two building agents may share one checkout only if neither commits, switches branch or runs `npm install` there. Otherwise each works in its own git worktree.
- Push, open a pull request, or merge only when the human asks. Never force-push, never skip hooks.

## Definition of Done for every sprint

The sprint's own Definition of Done in the roadmap comes on top of this list.

- [ ] Every job in `.github/workflows/ci.yml` passes on the integrated branch.
- [ ] `alembic check` is clean and the OpenAPI file is current.
- [ ] Each new endpoint has tests for the success case, validation failure, no session, and another user's resource.
- [ ] The sprint's core flow has a Playwright spec.
- [ ] No secret, credential or health data in the diff or in logs.
- [ ] New screens pass a keyboard-only run and respect `prefers-reduced-motion`.
- [ ] Reviewer verdict is `PASS`, and its report is on the sprint issue.

## Stop and ask the human

An agent stops and reports to the lead instead of deciding alone when the work would:

- add a paid service, a new third-party data processor, or a dependency with a non-permissive licence;
- change authentication, session, cookie or row-level-security behaviour beyond the sprint scope;
- drop or rewrite data in a migration;
- contradict an ADR in `docs/adr/`;
- touch production.
